Ai phát sự kiện: GameManager phát STATE_CHANGED và GAME_OVER. Mọi sự kiện "trong trận" (HP, trúng đòn, khiên vỡ, phase, bắn, loạt đạn, orb) do BattleBroadcaster phát. Đây là class thuần do GameManager sở hữu và gọi mỗi frame, nên vẫn nằm ở tầng controller. View và UI chỉ nghe, không bao giờ hỏi vòng model để biết HP đổi chưa.

ViewEvents chỉ có một hằng CANVAS_RESIZE: 'canvas-resize'. Đó là tên sự kiện của view trong engine, được CameraFollow, ScreenAdapter và PausePanel dùng. Gom vào một chỗ giống GameEvents để không có chuỗi tên sự kiện viết rời rạc trong code.

Vì sao tách như vậy: luật chơi đọc và kiểm tra được mà không cần mở editor; đổi giao diện không đụng luật; số lượng đạn tăng không làm tăng số component phải update. Cái giá: mỗi frame view phải chép dữ liệu sang node.

Một frame chạy thế nào

Thứ tự dưới đây đúng như trong code.

  1. Input đến theo sự kiện. KeyboardInput, VirtualJoystick ghi trục di chuyển vào InputState khi có phím hoặc chạm. Phím dash hoặc nút DASH gọi GameManager.requestDash(), hàm này chỉ nhận khi đang Playing.
  2. GameManager.update(dt) chỉ chạy khi state là Playing (khi Paused thì director.pause() đã dừng hẳn mọi update). Nó cắt frame thành các bước tối đa 50 ms, frame dài hơn 250 ms thì bỏ phần thừa. Mỗi bước cũng cộng vào RoundTimer.
  3. Mỗi bước gọi BattleWorld.step: player di chuyển → súng player (đếm phát bắn) → BossBrain (phase, chọn move/shot, chạy chúng; đếm loạt đạn) → rơi orb nếu boss vừa lên phase → đạn hai bên bay và bị xoá khi chạm tường → đạn player trúng boss → đạn boss và thân boss trúng player (khiên chặn trước) → player nhặt orb → trả về BattleOutcome.
  4. BattleBroadcaster.emitFrameChanges phát sự kiện HP, trúng đòn, khiên vỡ, phase chỉ khi giá trị đổi, và sự kiện bắn, loạt đạn, orb tối đa một lần mỗi frame nhờ so bộ đếm. Sau đó handleOutcome: boss chết thì xoá hết đạn, ghi kỷ lục thời gian rồi phát GAME_OVER.
  5. Trong lateUpdate, các view chép model lên node: PlayerView, BossView, hai BulletLayerView, CameraFollow, PickupView, DashTelegraphView, DashButton. Hiệu ứng (ImpactEffects, PhaseBanner) tự chạy theo thời gian; RoundTimerView chỉ đổi chữ khi sang giây mới.
  6. UI và hiệu ứng phản ứng theo sự kiện: thanh máu, nhãn phase, banner, bảng Game Over, menu pause, tia lửa, âm thanh, rung camera.
// controller/GameManager.ts
protected update(dt: number): void {
    if (this._state !== GameState.Playing || !this._world) {
        return;
    }
    const outcome = this.simulateFrame(dt, this._world);
    // NOTE: HP is broadcast before the outcome, so the HUD already shows 0 when GAME_OVER arrives.
    this.broadcaster.emitFrameChanges(this._world);
    this.handleOutcome(outcome, this._world);
}

private simulateFrame(dt: number, world: BattleWorld): BattleOutcome {
    // NOTE: frames longer than MAX_FRAME_TIME (tab switch, debugger) are cut, not fast-forwarded.
    let remaining = Math.min(dt, GameConfig.FRAME.MAX_FRAME_TIME);
    let outcome = BattleOutcome.None;
    while (remaining > 0 && outcome === BattleOutcome.None) {
        const step = Math.min(remaining, GameConfig.FRAME.MAX_DT);
        outcome = world.step(step, this._input);
        // NOTE: simulated time, not wall time: a cut long frame is not counted, so the clear time
        // matches what was actually played.
        this.roundTimer.advance(step);
        remaining -= step;
    }
    return outcome;
}
Vì sao sub-step: máy yếu chạy 15 fps thì dt ≈ 0.066 s. Nếu bước một lần, đạn player (900 px/s) nhảy 60 px mỗi bước và có thể "xuyên" qua mục tiêu. Cắt thành bước ≤ 50 ms vừa giữ đúng tốc độ thật, vừa giữ va chạm chính xác.
Vì sao sự kiện phát sau vòng lặp: một frame có thể chạy nhiều bước. Nếu phát sự kiện trong từng bước thì âm thanh bắn có thể kêu hai lần trong một frame. Phát một lần sau vòng lặp, dựa trên bộ đếm, thì mỗi frame tối đa một sự kiện mỗi loại.

BulletStoremodel/BulletStore.ts · 121 dòngmodel

Lưu toàn bộ đạn của một phe trong 4 mảng Float32Array cố định (x, y, vx, vy). Đạn đang sống nằm ở chỉ số [0, count). Không có object nào cho từng viên đạn.

/** Swap-remove: the last bullet takes the freed slot. */
private removeAt(index: number): void {
    // PERF: O(1) instead of shifting every later bullet (order does not matter for bullets).
    const last = this._count - 1;
    if (index !== last) {
        this.x[index] = this.x[last];
        this.y[index] = this.y[last];
        this.vx[index] = this.vx[last];
        this.vy[index] = this.vy[last];
    }
    this._count = last;
}
step(dt: number, bounds: ArenaBounds): void {
    // NOTE: loop backwards: removeAt moves the last bullet into slot i, and that bullet was
    // already processed, so nothing is skipped or moved twice.
    for (let i = this._count - 1; i >= 0; i--) {
        this.x[i] += this.vx[i] * dt;
        this.y[i] += this.vy[i] * dt;
        if (bounds.touchesWall(this.x[i], this.y[i], this.radius)) {
            this.removeAt(i);
        }
    }
}
Vì sao: không tạo object khi bắn, không rác cho GC, dữ liệu nằm liền nhau trong bộ nhớ nên duyệt nhanh. clear() chỉ đặt count = 0, đó là cách "xoá hết đạn ngay lập tức" khi boss chết. Sức chứa: đạn player 64, đạn boss 400.
Hỏi: vì sao duyệt ngược từ cuối mảng?
Vì removeAt(i) lấy viên cuối mảng đặt vào chỗ i. Viên cuối đó đã được xử lý rồi (đi ngược), nên không viên nào bị bỏ sót hay xử lý hai lần.

private outcome(): BattleOutcome {
    // NOTE: boss checked first, so a same-frame double kill counts as a victory.
    if (this.boss.health.isDead) {
        return BattleOutcome.BossDefeated;
    }
    if (this.player.health.isDead) {
        return BattleOutcome.PlayerDefeated;

Vì sao thứ tự này: mọi thứ di chuyển và bắn trước, đạn bay sau, va chạm xét cuối cùng trên vị trí đã chốt của frame. Hai bên cùng chết trong một frame thì tính là thắng. Hỏi: khi player đang bất tử, đạn boss xử lý thế nào?

GameManagercontroller/GameManager.ts · 225 dòngcontroller

Update gameplay duy nhất của cả game. Giữ BattleWorld, InputState, RoundTimer, BattleBroadcaster và state machine Ready → Playing ⇄ Paused, Playing → GameOver. Là nơi duy nhất đổi GameState và nơi duy nhất gọi director.pause() / resume().

/** Starts a new round without reloading the scene. Used by the start screen and both Restart buttons. */
startGame(): void {
    if (!this._world) {
        return;
    }
    this.resumeDirectorIfPaused();
    this.prepareRound();
    this.setState(GameState.Playing);
}
/**
 * Resets the world and the HUD, and leaves the game in Ready (nothing moves until Playing).
 * NOTE: passing through Ready lets every view clear the previous round (panel, camera snap).
 */
private prepareRound(): void {
    if (!this._world) {
        return;
    }
    this.setState(GameState.Ready);
    this._world.reset();
    this.roundTimer.startRound();
    this._input.isDashRequested = false;
    this.broadcaster.emitRoundStart(this._world);
}
Vì sao: chơi lại không cần load lại scene, chỉ đi qua Ready để mọi view tự dọn. prepareRound() dùng chung cho lần mở game đầu, Restart, và Home trong menu pause. World tạo trong onLoad (không trong field initializer) vì editor cũng khởi tạo component khi mở scene. Kỷ lục thời gian đọc từ SaveStore một lần trong onLoad.
Hỏi: vì sao round đầu được chuẩn bị trong start() chứ không trong onLoad()?
Mọi onEnable (nơi view đăng ký nghe sự kiện) chạy trước mọi start. Gọi prepareRound() trong start thì sự kiện HP và phase ban đầu chắc chắn có người nghe. Round đó dừng ở Ready sau màn hình bắt đầu, tới khi StartScreen gọi startGame(). Trên web, chạm có thể tới trước start(), nên start() chỉ chuẩn bị khi state vẫn là Ready.

private emitHealthChange(health: Health, lastHp: number, hpEvent: string, hitEvent: string): number {
    const hp = health.current;
    if (hp === lastHp) {
        return lastHp;
    }
    if (hp < lastHp) {
        EventBus.emit(hitEvent);
    }
    EventBus.emit(hpEvent, hp, health.max);
    return hp;
}

// controller/GameManager.ts
pause(): void {
    if (this._state !== GameState.Playing) {
        return;
    }
    this.setState(GameState.Paused);
    director.pause();
}

resume(): void {
    if (this._state !== GameState.Paused) {
        return;
    }
    // NOTE: the director runs again before Playing is broadcast, so listeners see a live engine.

private fireVolley(origin: Point, target: Point, emitter: IBulletEmitter): void {
    // PERF: atan2 once per volley for the aim direction; the per-bullet cos/sin run only when a
    // volley fires (about once a second), not every frame.
    const baseAngle = Math.atan2(target.y - origin.y, target.x - origin.x);

export function circleOverlapsBox(
    cx: number, cy: number, r: number, boxX: number, boxY: number, halfSize: number,
): boolean {
    // The point of the square closest to the circle centre; the circle overlaps if that point is inside it.
    const nearestX = clamp(cx, boxX - halfSize, boxX + halfSize);
    const nearestY = clamp(cy, boxY - halfSize, boxY + halfSize);
    const dx = cx - nearestX;
    const dy = cy - nearestY;
    // PERF: squared distance, no Math.sqrt.
    return dx * dx + dy * dy < r * r;
}

private move(dt: number, dirX: number, dirY: number, bounds: ArenaBounds): void {
    // Keyboard and joystick are added so either one works; the sum is normalised below.
    const lengthSqr = dirX * dirX + dirY * dirY;
    if (lengthSqr === 0) {
        return;
    }
    // NOTE: only shrink, never grow: a diagonal key press (length ~1.41) is scaled to 1 so it is not
    // faster, while a half-tilted joystick (length < 1) keeps its slower speed.
    if (lengthSqr > 1) {
        const scale = 1 / Math.sqrt(lengthSqr);
        dirX *= scale;
        dirY *= scale;
    }
    const distance = PLAYER.SPEED * dt;
    this.moveClamped(dirX * distance, dirY * distance, bounds);
}

Tự đánh giá code: điểm mạnh và chỗ cần cải thiện

Biết điểm yếu của chính code mình là cách tốt nhất để biết bước tiếp theo nên làm gì.

MẠNH

Mô phỏng tách khỏi engine

model/ không import cc, một update duy nhất, view chỉ chép dữ liệu. Luật chơi chạy và test được ngoài Cocos.

MẠNH

Đạn và hiệu ứng không tạo rác

Typed array cố định, swap-remove, slot node đạn và node burst tạo sẵn: không cấp phát trong vòng lặp nóng.

MẠNH

Mở rộng boss bằng dữ liệu

Interface + factory + bảng phase; thiếu entry là lỗi biên dịch.

MẠNH

Pause không làm lệch state

Một nơi duy nhất gọi director.pause() / resume(); mọi đường thoát (Restart, Home, huỷ scene) đều resume trước.

MẠNH

Lưu game an toàn

SaveStore có version, coi dữ liệu là unknown, kiểm từng trường, không bao giờ throw.

CẦN BIẾT

Chưa có unit test

Model thuần TS rất dễ test nhưng repo chưa có test nào.

Hướng cải thiện: viết test cho Collision, góc của FanShot, chuyển phase của BossBrain, RoundTimer.recordVictory, formatTime và SaveStore.sanitize, vì chúng không phụ thuộc engine hoặc chỉ cần giả localStorage.

CẦN BIẾT

Ngẫu nhiên không có seed

Math.random được dùng trực tiếp trong MathUtil (chọn move/shot, vị trí orb) và rung camera, nên không tái hiện được đúng một trận để debug hay replay.

Cách sửa: truyền một bộ sinh số ngẫu nhiên có seed vào BossBrain và PickupModel.

CẦN BIẾT

Va chạm rời rạc, an toàn nhờ sub-step

Không dùng va chạm quét (swept). Hiện an toàn vì bước tối đa 50 ms; nếu đạn player nhanh hơn khoảng 2700 px/s thì có thể xuyên qua boss.

CẦN BIẾT

Luật riêng cho UI lúc pause

Vì dùng director.pause(), popup nào hiện trong lúc pause cũng không được mở bằng tween và phải tự gọi updateAlignment(). Hiện chỉ có menu pause và nó làm đúng, nhưng người thêm UI mới phải biết luật này.

CẦN BIẾT

Phím có thể bị "kẹt" khi mất focus

KeyboardInput quên phím đang giữ khi trang bị ẩn (EVENT_HIDE). Nhưng nếu canvas chỉ mất focus mà trang vẫn hiện (bấm ra ngoài) thì không có sự kiện nào, player đi tiếp tới khi nhấn và nhả lại phím đó. Đã ghi trong comment là giới hạn chấp nhận.

NHỎ

Tên sự kiện kiểu string

emitHealthChange(..., hpEvent: string, hitEvent: string) trong BattleBroadcaster không ràng buộc payload theo từng sự kiện; sai tham số chỉ lộ ra lúc chạy.

NHỎ

Vài comment chưa theo kịp việc tách BattleBroadcaster

Đầu GameEvents.ts vẫn ghi "GameManager is the only emitter of gameplay events", PickupModel ghi "GameManager reports where it appeared", trong khi người phát thật là BattleBroadcaster (do GameManager sở hữu). README cũng còn ghi "about six lateUpdates" trong khi code có 12 component dùng lateUpdate.

Hướng cải thiện: sửa các dòng này để comment khớp code.

NHỎ

Kho đạn đầy thì bỏ viên mới

Vượt sức chứa (player 64, boss 400) thì viên mới bị bỏ và có một console.warn mỗi kho. Với nhịp bắn hiện tại không xảy ra (đỉnh dưới 100 đạn boss), nhưng nên biết khi tăng độ khó.

NHỎ

Phase chỉ đi tiến

Đúng với đề vì boss không hồi máu; nếu thêm hồi máu thì phải bỏ điều kiện này trong updatePhase, và orb khiên cũng dựa vào phase chỉ tăng.

NHỎ

Chưa có bản build Windows

Máy không có Visual Studio; nộp bản Android APK và web-mobile.
